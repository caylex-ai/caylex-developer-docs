[Background Sync](/background-tasks/background-sync) collects content from connected services and returns it as one uniform JSON export.
These recipes show how to run it from your backend and load the results into a
search index, RAG pipeline, or knowledge base.

## The common pattern

Every recipe follows the same steps. Only the last one depends on the source:

1. **Find the servers you can sync** with `GET /sync-configs/sources`. Only
   servers that support Background Sync are listed.
2. **Create or update a sync config** naming the servers, the users to sync
   as, and what to collect. Look the config up by name first so the recipe is
   safe to re-run.
3. **Trigger it** with `POST /sync-task`, optionally passing `since` to collect
   only recent changes. Caylex starts one sync run per user and returns a
   `trigger_id` for the whole trigger plus a `sync_id` for each run.
4. **Poll each run** with `GET /sync-task/{sync_id}` until it's `completed`,
   `incomplete`, or `failed`. To check every run at once, list them with
   `GET /sync-task?trigger_id={trigger_id}`. The `trigger_id` has no status
   of its own, and the per-run endpoints accept only a `sync_id`.
5. **Download the export** by paging through
   `GET /sync-task/{sync_id}/export`.
6. **Load the resources** into your system. Each source has its own content
   format, relations, and attachments.

<Warning>
Exports contain complete customer documents, database rows, comments, and other
sensitive content. Keep the platform token and every export server-side, apply
your normal retention controls, and never commit exports to source control.
</Warning>

## Endpoints used

| Method & path | Purpose |
| --- | --- |
| `GET /api/v1/sync-configs/sources` | List the project's servers that support Background Sync. |
| `GET /api/v1/sync-configs` | Find an existing config by name. |
| `POST /api/v1/sync-configs` | Create a config. |
| `PUT /api/v1/sync-configs/{id}` | Replace a config's servers, users, and instructions. |
| `POST /api/v1/sync-task` | Trigger a config: one run per user. |
| `GET /api/v1/sync-task?trigger_id={trigger_id}` | List one trigger's runs with their statuses. |
| `GET /api/v1/sync-task/{sync_id}` | Poll a run's status. |
| `GET /api/v1/sync-task/{sync_id}/export` | Page through the run's export. |
| `POST /api/v1/sync-task/{sync_id}/continue` | Resume sources that stopped short. |

## Loading an export

Every export uses the same resource shape, so most loading logic is shared
across sources:

- **Key on `key`.** It's `{source_type}:{server_instance_id}:{native_id}`, and
  it stays the same across runs and across users of the same server.
- **Skip unchanged resources** by comparing `content_hash` with your stored copy.
- **Index `content.text`** using `content.format` to pick a parser. Index
  `available` resources, flag `partial` ones, and store `metadata_only` ones
  without a body.
- **Keep the structure.** `relations` link resources to their parents,
  children, and rows; `attachments` carry related data such as database rows,
  comments, or file permissions.
- **Track access.** Each run collects as one user. If your index enforces
  per-user access, record which users' runs returned each `key`.
- **Check before you replace.** Read each source's `status` and `counts` before
  overwriting data. Treat a key that's missing from an export as deleted only
  after a full sync, without `since`, where the run is `completed` and every
  source is `ok`.

The [export format](/background-tasks/background-sync#export-format) reference
describes every field.
