# Incident API

[Overview](/api-monitoring-fixture/overview) · [List incidents](/api-monitoring-fixture/list-incidents) · [Get an incident](/api-monitoring-fixture/get-incident) · [Create an incident](/api-monitoring-fixture/create-incident)

This is a fictional API reference for testing API-documentation ingestion and monitoring. It does not describe a working API. The base URL is `https://api.example.com/v1`.

## Authentication and shared behavior

Every request requires an `X-API-Key` header containing a project API key. Send and receive JSON with `Content-Type: application/json`. Timestamps use RFC 3339 UTC. Clients may retry `GET` requests; for `POST` requests, send an `Idempotency-Key` header containing a unique string so a retry does not create a second incident.

Successful responses return the resource directly, except list responses, which use the pagination envelope described below. Errors use the shared error schema. A missing or invalid API key returns HTTP `401` with error code `unauthorized`.

## Shared JSON schemas

All three endpoint pages use this `Incident` object:

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | string (UUID) | Stable incident identifier. |
| `title` | string | Human-readable summary. |
| `severity` | `low` \| `medium` \| `high` \| `critical` | Operational impact. |
| `status` | `open` \| `acknowledged` \| `resolved` | Current lifecycle state. |
| `reporter` | object | `{ "id": string, "display_name": string }`. |
| `created_at` | string (date-time) | Creation time in UTC. |
| `updated_at` | string (date-time) | Most recent change in UTC. |
| `metadata` | object | Optional string-to-string labels supplied by the caller. |

Example `Incident`:

```json
{
  "id": "8a65861a-d78e-4330-8763-18e8cb67c190",
  "title": "Checkout latency is elevated",
  "severity": "high",
  "status": "open",
  "reporter": { "id": "usr_42", "display_name": "Taylor" },
  "created_at": "2026-10-06T12:00:00Z",
  "updated_at": "2026-10-06T12:00:00Z",
  "metadata": { "service": "checkout" }
}
```

List responses have `{ "data": [Incident], "next_cursor": string | null }`. Pass a non-null `next_cursor` as the next request's `cursor` to continue. An error response has `{ "error": { "code": string, "message": string }, "request_id": string }`.
