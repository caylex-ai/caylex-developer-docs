Create and manage incidents for your project. The base URL is `https://incident-api.caylex.run/v1`. Requests and responses use JSON.

## Get started

Create an incident using a [project API key](/api-monitoring-fixture/authentication):

```bash
curl -X POST https://incident-api.caylex.run/v1/incidents \
  -H "X-API-Key: $INCIDENT_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: checkout-latency-2026-10-06" \
  -d '{"title":"Checkout latency is elevated","severity":"high","reporter_id":"usr_42"}'
```

The response includes an `id` you can use to [retrieve the incident](/api-monitoring-fixture/get-incident), [update it](/api-monitoring-fixture/update-incident), or [add a comment](/api-monitoring-fixture/add-comment).

## Incident object

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | string (UUID) | Stable incident identifier. |
| `title` | string | Human-readable summary. |
| `severity` | `low` \| `medium` \| `high` \| `critical` | Operational impact. |
| `status` | `open` \| `acknowledged` \| `resolved` | Current lifecycle state. |
| `service_id` | string or `null` | Service affected by the incident. |
| `assignee` | object or `null` | Assigned responder: `{ "id": string, "display_name": string }`. |
| `reporter` | object | `{ "id": string, "display_name": string }`. |
| `created_at` | string (date-time) | Creation time in UTC. |
| `updated_at` | string (date-time) | Most recent change in UTC. |
| `resolved_at` | string (date-time) or `null` | Resolution time, if resolved. |
| `resolution` | string or `null` | Summary of the fix, if resolved. |
| `resolution_code` | `fixed` \| `mitigated` \| `duplicate` \| `not_reproducible` \| `null` | How the incident was resolved. |
| `metadata` | object | Optional string-to-string labels supplied by the caller. |

```json
{
  "id": "8a65861a-d78e-4330-8763-18e8cb67c190",
  "title": "Checkout latency is elevated",
  "severity": "high",
  "status": "open",
  "service_id": "svc_checkout",
  "assignee": null,
  "reporter": { "id": "usr_42", "display_name": "Taylor" },
  "created_at": "2026-10-06T12:00:00Z",
  "updated_at": "2026-10-06T12:00:00Z",
  "resolved_at": null,
  "resolution": null,
  "resolution_code": null,
  "metadata": { "service": "checkout" }
}
```

Comments have an `id`, `incident_id`, `body`, `visibility` (`public` or `internal`), an `author` with `id` and `display_name`, and a `created_at` timestamp.

## Services and responders

A service groups incidents for one product or system. Its `id` is stable; `name` is unique within a project. The `status` is `active` or `archived`. Archived services remain on existing incidents but cannot be assigned to new ones.

```json
{
  "id": "svc_checkout",
  "name": "Checkout",
  "description": "Customer checkout and payment authorization",
  "status": "active",
  "created_at": "2026-09-18T10:00:00Z",
  "updated_at": "2026-09-18T10:00:00Z"
}
```

A responder has an `id`, `display_name`, `email`, and `active` flag. Only active responders can be assigned to incidents. The [responder directory](/api-monitoring-fixture/list-responders) is read-only; manage membership in project settings.

## Incident events

The [incident timeline](/api-monitoring-fixture/list-incident-events) records changes to status, severity, assignee, and service. Each event has an `id`, `incident_id`, `type`, `actor` (`id` and `display_name`), `created_at`, and a `details` object containing the changed values. Events are immutable.

## Pagination and errors

List endpoints return `{ "data": [...], "next_cursor": string | null }`. Pass `next_cursor` as the next request's `cursor` until it is `null`. Cursors are opaque and may expire; an expired cursor returns `400 invalid_cursor`.

Errors use the same format across routes:

```json
{
  "error": { "code": "invalid_request", "message": "severity must be one of low, medium, high, critical" },
  "request_id": "req_01J9K7M4XQ"
}
```

Include `request_id` when contacting support. Timestamps are UTC. Send an `Idempotency-Key` on create requests so retries do not create duplicates.
